# 2.1.3 · Gecko 网页可见 CPU 线程数上限

版本号 `2.1.3`，版本代码 `105`。本页说明实现范围，正式安装包及生产验证结果以 GitHub Release 为准。

## Gecko 原生 CPU 上限

沿用现有 GeckoView 和 Android System WebView 内核，为当前 Gecko 环境增加“内核默认、最多 1、最多 2”三个网页可见 CPU 线程数选项。它控制原生 `navigator.hardwareConcurrency` 的暴露上限，不修改手机的处理器、CPU 型号或实际调度能力，也不承诺加速网站。

设置按环境加密保存。一个环境进程中的 Gecko 页面、弹窗和 Worker 共用同一个运行时，因此这不是每个标签页单独的硬件设置。保存后的选择只在该环境下一次真正冷启动时应用；保存操作不重载网页、不结束进程，也不打断当前回复或上传。关闭页面或返回列表不一定会结束后台引擎。

强化保护继续优先。它可能继续向网页暴露内核统一值，即使原生 CPU 偏好的回读值为 1 或 2，也不能据此宣称网页已按该上限生效。配置保存、原生回读和页面实际观测必须分开显示。

## 已有独立能力证据

同版本内核的独立 Android 诊断中，标准模式的新页面、Dedicated、Blob、Shared 和新注册的 Service Worker 均通过原生 getter 观察到默认值、2、1、恢复默认的变化。强化保护模式在所有上下文保持其统一值，测试没有关闭该保护。这个诊断使用固定原生偏好，不替换 JavaScript getter。

该能力证据不替代本版的实际设置保存、原生 SDK 接口、首次加载、冷启动、持久 Service Worker 恢复、默认值恢复或多环境并发验收。正式安装包必须通过这些验收。

正式 2.1.3 还必须通过额外的组合专项：同一安装包、环境进程和原生页面，在冷启动 CPU 上限为 1 且保留默认 IP 时区时，由首个内联脚本同时读取原生 CPU 值与纽约 Date／Intl 时区，并核对同一浏览器代理的受控 IP 响应、原生上下文及持久配置。原 CPU 十个案例和 IP 十一个案例仍分别保留，组合专项不替代它们。此前 `0111cec` 的独立诊断结果不能作为新组合版本的发布资格。

## 自动连接检测

本阶段增加按环境保存的自动连接检测开关。关闭后停止自动排队和执行外部网络响应检测，减少后台请求；默认保持开启，用户仍可主动进行手动测量。开关不会改变网页代理线路或网络准入保护。

## 范围限制

Chromium 尚未实现原生 CPU 上限、独立时区或 TLS 策略接口。本版不伪造硬件型号、内存、GPU 或完整设备身份。

Gecko 默认 IP 时区沿用 2.1.2 的原生页面与 Worker 范围；Service Worker 的时区仍使用系统值，不能将 CPU 的 Service Worker 覆盖误认为时区也已覆盖。

现有内核的真实生产诊断已观察到一个运行中切换保护的边界：在 CPU 上限为 1 的环境中应用强化保护模板后，新页面及新 Dedicated、Blob、Shared Worker 的原生 getter 值为 4，但已存在的 ServiceWorker 仍保留启动时的值 1。因此不能承诺切换模板会即时统一所有存活后台任务。要让这些已有 ServiceWorker 也统一采用新保护，需要当前环境真正冷启动；保存 CPU 设置或切换模板不会自动结束当前任务。

同一诊断中，冷启动强化保护的五类上下文均为 4；相同持久配置的 ServiceWorker 冷恢复和两个环境并发的五类原生 getter 也分别通过。以上是绑定特定源码和安装包的实际结果，原生偏好回读仍不等于页面效果或完整指纹保护，广泛覆盖标记继续为 false。

TLS、HTTP/2 和 HTTP/3 策略仍留在后续独立阶段，本版不声称具备任意 Chrome 或其他浏览器的 TLS 握手指纹模拟能力。
