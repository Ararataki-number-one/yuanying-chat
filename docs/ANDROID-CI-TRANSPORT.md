# Android 发布测试连接

产品仍使用单 GeckoView、各环境独立存储与固定出口。以下只描述临时 CI 模拟器的连接准备，不改变应用或输入驱动。

在 API 35 r09 的 VSOCK 路径上，实际安装 APK 的读取曾出现中途断开；固定模拟器 36.3.10、ADB 35.0.2 和分段读取均没有单独消除问题。失败保留为失败，不以诊断成功、后续光标成功或别次构建替代缺失的字节校验。

原生 TCP 的准备还暴露了独立的网络时序问题：首次 SDK 设置程序拥有最初的 Wi-Fi 请求。停用它后，即使即时 ConnectivityManager 快照健康，Wi-Fi 地址也可能随后消失。若此时已经改走 Wi-Fi 上的 TCP，网络前置检查本身就会失联。

新的准备顺序：

1. 在固定的 `emulator-5556` 启动连接上安装本次 APK，核对实际 QEMU、源码与安装身份，并运行原有网络准备逻辑。
2. 确认 SDK 设置程序已停用，完成旧 Wi-Fi 连接的撤销，通过原有逻辑重新连接实际观察到的 SDK `AndroidWifi`，读取并验证带新 nonce 的真实 CM 状态。
3. 创建原生 TCP 转发，用 QEMU 的只读 `info usernet` 核对实际目标为 `mynet` 上的 `127.0.0.1:5555 → 10.0.2.15:5555`。这条 TCP 路径独立于 Wi-Fi 地址的撤销。
4. 所有正式用例仍针对原有 `emulator-5554`，再次执行未修改的正常前置检查，再运行原来的 APK 字节、ZIP/DEX、SDK、源码、IME、启动器和输入断言。

`host:emulator` 是单向注册通知，不返回普通服务的 `OKAY`。实现依照 [AOSP 的通知测试](https://github.com/mirror/platform_packages_modules_adb/blob/1cf2f017d312f73b3dc53bda85ef2610e35a80e9/test_adb.py) 发送帧后关闭，再用真实 `get-state` 确认设备就绪。先前误加的 `OKAY` 判断使 eb927 构建的七个设备在启动阶段停止，未运行输入用例；该失败保留为失败，后续使用新源码重新构建。

独立诊断 [39923380038](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39923380038) 在全新实例上比较默认转发和显式 Wi-Fi 转发，每个实例预先规定 64 次完整实际安装 APK 读取；诊断结果不授予应用验收。第一个默认转发实例的 64 次大小、SHA256 和定义检查全部通过，最慢约 4.62 秒。其余观测继续保留，正式发布仍须同一最终源码、构建和尝试的全部门禁与三组独立输入测试通过。

没有重放原始输入用例、放宽断言或时限、重读失败的 APK 分段、以编译产物替代设备字节、改动认证/防火墙或收集包内容。模拟器通过不等于真机、百度输入法或真实 ChatGPT 账号上传通过。
