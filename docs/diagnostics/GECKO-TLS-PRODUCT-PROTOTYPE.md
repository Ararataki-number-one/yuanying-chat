# Gecko TLS cold policy prototype

This branch prepares a production integration for review. Its base is public `9f5d8913060f3b97c042120570eb5bfcb71e5dd8`, an existing-CPU working source with a successful standalone native TLS capability diagnostic. This is not the latest qualified IP/CPU release base. No production TLS release or per-environment acceptance is claimed here.

The current environment can save **kernel default** or **TLS1.3 only**. The desired record is encrypted and fenced by environment UUID, generation and revision. Saving updates the pending choice only. It does not reload a page, apply native preferences to an active runtime, restart a process or end replies/uploads/downloads. A genuine cold start is required; reopening an interface is insufficient.

At cold startup, background environment I/O validates the existing anchored profile, reconciles only the two owned TLS USER preference keys, and preserves all unrelated profile bytes. The original CPU/closed-route startup YAML stays intact; strict mode appends only native min/max4/4. Default mode adds no numeric range and reads the actual native defaults. A bounded, in-memory preparation receipt records the actual pre-runtime non-TLS byte hashes and preserved config prefix. It does not compare an entire live profile after Gecko legitimately flushes preferences.

The sole Gecko runtime must confirm the expected native DEFAULT/effective min/max and absence of residual USER overrides before ordinary sessions, navigation, restore, popup and Gecko route admission. CPU and original native protection gates remain conjunctive. Late callbacks, foreign runtime/identity, stale startup state, USER overrides and timeouts cannot release admission. A later saved desired revision stays pending and cannot replace the immutable active boot. RFP, HTTP/2 and HTTP/3 preferences are read without TLS policy writes.

The scope is **Gecko web connections** and only separately measured worker connections using that native stack. The app's independent downloader, connection checks and proxy entrance can use Java or other TLS stacks; they are not covered by this setting or by a Gecko NSS readback. Chromium/System WebView exposes no independent per-environment TLS-version interface here. No system TLS setting, TLS1.0/1.1 option, MITM of user traffic, debug port, JA3/JA4 impersonation, arbitrary GREASE control or full TLS fingerprint emulation is introduced.

The standalone Android diagnostic observed DEFAULT3/4 → DEFAULT4/4 → DEFAULT3/4. USER values were null throughout, so it proves restoration of absence, not restoration of a nonempty USER value. Four fresh actual ClientHellos independently proved default TLS1.2 success, strict TLS1.2 handshake rejection, strict TLS1.3 success and restored TLS1.2 success. Rejection is evidenced by actual OpenSSL `SSLError/UNSUPPORTED_PROTOCOL` and exact-target native security category2/code34; no separate fatal-alert-packet bytes were captured or decoded. RFP remained false; H2/H3 settings stayed enabled, ALPN offers stayed h2/HTTP1.1, and the controlled peers negotiated HTTP1.1. Strong-RFP interaction, H2 transport and QUIC are not inferred from that diagnostic.

Production acceptance must independently exercise actual MainActivity/ChatSession, encrypted desired state, first native network request, nonempty old USER cleanup, cold default restoration, strong RFP, concurrent environments, actual UI pending-save behavior and any claimed persistent ServiceWorker fetch. The standalone diagnostic, JVM hosts and SDK compilation cannot replace those checks. Final release requires rebasing onto the qualified IP/CPU source, preserving all old gates, fresh full qualification plus the TLS product gate, and the original release signer.
