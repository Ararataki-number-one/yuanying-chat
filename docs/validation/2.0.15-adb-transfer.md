# 2.0.15 installed-APK transfer interruption

Source `a7050a430ccca2036cd404291653db321c7fed8a`, integration run
[39887315606](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39887315606),
is not a qualified release cohort. All five main Android phases and extra
editing sample 2 passed. Extra editing sample 1 failed before its original
performance workload: its one `adb pull -Z` of the installed APK returned 1
after approximately 0.49 seconds, with only a 31% progress line. The ADB client
deleted the partial transfer. This was not the 30-second timeout, a disk-full
failure, or an observed input assertion failure. The subsequent caret fixture
still ran independently; it cannot replace the missing performance evidence.

The separate [transfer diagnostic run 39890007264](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39890007264)
used the same APK bytes, stock emulator and system image. All 20 predeclared
read-only transfers matched size and SHA256. It did not run input workloads,
did not reproduce the interruption, and supplies no application acceptance.
The underlying transport cause remains undetermined.

The next source adds bounded client protocol diagnostics to the same single
installed-APK read. It retains the original transfer command, private staging,
30-second deadline, exact size/SHA256 and actual ZIP/DEX/source audits. There
is no retry, compiled-file fallback, changed input pacing, or relaxed oracle.
Tracing is limited to the host byte read before/after the input workload.

Run one complete new cohort with the existing three predeclared independent
editing samples. Require every sample and every original release gate to pass
on the same source. Preserve this interrupted cohort and its diagnostic run
regardless of the new result; do not describe the underlying transport as fixed
unless subsequent evidence identifies and corrects its cause.

## Raw-stream failure and framed completion

Source `6fc6e9834b6332f4508a373224328852989ce881`, run
[39893645542](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39893645542),
also remains unqualified. Sample 1's after-read returned zero but transferred
122932736 of 126161006 bytes; its following caret preflight also received a
short stream. The exact byte guard correctly rejected both. Thus SYNC alone
does not explain this environment's truncation.

The separate [framing diagnostic 39895027356](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39895027356)
ran the original performance driver once and twenty fixed alternating reads,
without syscall tracing: ten `exec-out cat` and ten `shell -T cat`. All twenty
matched the actual APK's exact size and SHA256. This still does not reproduce
or identify the underlying intermittent truncation.

The AOSP client's [legacy exec copy](https://github.com/mirror/platform_packages_modules_adb/blob/main/client/commandline.cpp)
can finish without a successful remote completion status: the `exec-out`
caller ignores `copy_to_file`'s boolean result. Its shell-v2 reader instead
starts with exit code 255 and consumes the explicit remote exit-status frame.
This explains why a raw read may return zero after interruption; it is not
proof of the interruption's underlying cause.

Use one `adb shell -T cat <canonical-pm-path>` as the primary read. On the
pinned API 35 guest, this is framed shell v2 with PTY allocation disabled.
Capture binary stdout into Python, then write the exclusively reserved
destination; avoid the legacy direct stdio-to-file copy. Retain partial
timeout bytes in size/hash diagnostics without decoding APK contents into
public log text. Keep the same deadline, once-only invocation, nonzero-exit
and exact byte checks, actual APK audits, owned-file cleanup and no fallback.
The input drivers, timing and all release oracles remain unchanged.

Require every original gate and all three independent input samples in one
new source-bound cohort. None of the three interrupted cohorts or three
diagnostic runs can substitute for that qualification.

## Reproduced whole-device transport loss

The read-only [daemon observation run 39899280619](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39899280619)
used the exact `10f650a4c0043edada7b865ae0845a6644ecdbcf` APK, emulator
37.2.12 and API 35 Google APIs revision 9 image. It ran no editing workload
and grants no application acceptance. The default-daemon job completed its
24 fixed observations. In the sockets-traced job, observation 9 transferred
only 42115072 of 126161002 bytes, then the entire emulator transport went
offline. The following fixed observations recorded offline/missing-device
errors before the connection recovered; they are diagnostic observations,
not replacement release samples.

At the interruption the host daemon logged `connection terminated: read
failed`; guest `adbd` logged `connection terminated: write failed`. Host ADB
PID 2442 and guest adbd PID 437 survived. Before the interruption and after
reconnection, the installed file had the same 126161002-byte size and SHA256
`2a4fb026ebbd3ee8c320c82a89792671bd1d32fc7d8607b5b7a56573732b2ac0`.
The diagnostic stat command incorrectly passed a format containing spaces
through the Android shell; its size output is corroborative only and its
nonzero status remains preserved. The complete device SHA256 commands both
returned zero. Subsequent diagnostics use a colon-separated stat format.

This identifies a whole emulator ADB transport disconnect rather than an
input assertion failure or a changed installed APK. It does not yet identify
the failing kernel operation. The packaged emulator enables
`VirtioVsockPipe` by default. The emulator's
[ADB service selection](https://github.com/mirror/qemu-android/blob/e111ba9b1d03f295d5a208242cf9698cfaa29c4e/android/android-emu/android/adb-server.cpp)
selects `AdbVsockPipe` when enabled and `AdbGuestPipe` otherwise. A separate
backplane comparison keeps the APK, SDK, emulator version, image and byte
reader fixed and changes only this emulator prerequisite. No release gate
or input pacing is relaxed.

## Native guest TCP prerequisite

The [backplane comparison 39899833756](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39899833756)
did not establish an ADB connection within 180 seconds with
`VirtioVsockPipe` disabled. That configuration was rejected before any
editing workload; it is not used for acceptance.

The [native TCP diagnostic 39900377328](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39900377328)
retains the emulator's default feature flags, exact emulator/image/APK and
unchanged one-shot byte reader. It boots the same one guest on console 5556
and proxy 5557, forwards host TCP 5555 to guest adbd TCP 5555 using the
emulator's native redirection, then restarts the host ADB server during
setup so it discovers that real TCP transport as `emulator-5554`. There is
no device-name alias, substituted APK, or byte-read retry. The original
vsock transport at `emulator-5556` reaches this same guest and is not an
independent device or an input sample. Every fixture still explicitly uses
the original `emulator-5554` serial.

All 24 fixed TCP observations matched the 126161002 actual installed bytes,
SHA256 and original definition audit. Both device-side stat and SHA256
commands returned zero before and after; size, inode and modification time
were unchanged. Redirection and actual device-list receipts are retained in
the diagnostic artifact. This is a workaround for the observed emulated
vsock connection loss, not a claim to have repaired its underlying kernel
operation. It ran no editing workload and grants no release acceptance.

Use this native TCP prerequisite in every Android acceptance VM, retaining
the same SDK, image, graphics, memory, cores, once-only workloads, input
pacing, IME/launcher restoration and all byte/source/ZIP/DEX checks. Keep the
setup redirection/device-list text separate for each Android phase. Require
one entirely new source-bound cohort with all original gates and all three
predeclared independent editing samples before publication.
