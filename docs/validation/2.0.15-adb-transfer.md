# 2.0.15 installed-APK transfer interruption

Source `a7050a430ccca2036cd404291653db321c7fed8a`, integration run
[39887315606](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39887315606),
is not a qualified release cohort. All five main Android phases and extra
editing sample 2 passed. Extra editing sample 1 failed before its original
performance workload: its one `adb pull -Z` of the installed APK returned 1
after approximately 0.49 seconds, with only a 31% progress line. The ADB client
deleted the partial transfer. This was not the 30-second timeout, a disk-full
failure, or an observed input assertion failure. The subsequent caret fixture
still ran independently; it cannot replace the missing performance evidence.

The separate [transfer diagnostic run 39890007264](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39890007264)
used the same APK bytes, stock emulator and system image. All 20 predeclared
read-only transfers matched size and SHA256. It did not run input workloads,
did not reproduce the interruption, and supplies no application acceptance.
The underlying transport cause remains undetermined.

The next source adds bounded client protocol diagnostics to the same single
installed-APK read. It retains the original transfer command, private staging,
30-second deadline, exact size/SHA256 and actual ZIP/DEX/source audits. There
is no retry, compiled-file fallback, changed input pacing, or relaxed oracle.
Tracing is limited to the host byte read before/after the input workload.

Run one complete new cohort with the existing three predeclared independent
editing samples. Require every sample and every original release gate to pass
on the same source. Preserve this interrupted cohort and its diagnostic run
regardless of the new result; do not describe the underlying transport as fixed
unless subsequent evidence identifies and corrects its cause.

## Follow-up and byte-reader change

The new source `64b3d775e2596f585c9885dbe57b9ea1ae9556e2`, run
[39890927070](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39890927070),
also remains unqualified. Sample 1's original performance report passed all
160 checks and its caret report passed all 129 checks. Its **after** installed
APK read failed at a 66% progress line, returning 1 after about 0.69 seconds;
the SYNC client again deleted the partial file. This still prevents the required
before/after identity sidecar, and no input result waives that requirement.

Separate [loaded transport diagnostic 39892752568](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/39892752568)
ran the unchanged original performance driver once, then 20 predeclared
alternating observations: ten SYNC pulls and ten raw `exec-out cat` reads.
Every observation matched the actual selected APK's 126161002 bytes and
SHA256 `b790399b8c0fee7a831881d897ffe6e69151a9138cef3e47b766f357fe89cf4a`.
This confirms raw binary streaming works in this loaded test environment; it
does **not** identify the intermittent SYNC cause or qualify a release.

The byte reader now uses one primary `adb exec-out cat <canonical-pm-path>`
command, directing binary stdout into an exclusively reserved open file
descriptor. It retains the strict path whitelist, 30-second deadline,
nonzero-exit rejection, exact size/SHA256, actual ZIP/DEX/source audits,
owned-partial cleanup and no retry/fallback. A short stream remains observable
in the receipt before cleanup, rather than being erased inside the ADB client.
No input driver, input timing, IME/launcher guard or application code changes.
The reader's real subprocess controls reject empty/short/wrong bytes, progress
text, nonzero exits, timeouts, existing destinations and replaced pathnames.

The changed reader requires one complete new source-bound cohort, including
all three predeclared input samples and all original release gates. Keep both
interrupted cohorts and both separate diagnostic runs in the record.
