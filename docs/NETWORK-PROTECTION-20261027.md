# 网络保护专项第一轮（2026-10-27，东京）

本轮以正式版 2.0.22 的生产逻辑为基线，在隔离测试包中执行真实 Android 35／Gecko 157 对照。目标是受控私有 HTTPS 服务器，测试具有明确的 URL／临时证书例外和合成启动准入；不是 ChatGPT 官网、完整正常启动流程或用户手机验收。

| 用例 | 修复前 | 最小补丁后 | 结论范围 |
| --- | --- | --- | --- |
| 普通访问正控 | 四项操作成功，服务器七个应用事件 | 同样成功 | 只证明受控目标可达 |
| 完整默认路由的 VPN 黑洞 | 目标进入非转发 TUN | 仍允许准入，目标包进入 TUN | 黑洞不提供实际网站服务，不能当 VPN 可用性或完整防泄漏通过 |
| VPN 分流遗漏目标 | VPN 标记正常，但网页、Worker、WebSocket 能到达目标 | 零次直连准入、八次拒绝，服务器零个对应应用事件 | 此稳态新请求准入缺口修复有效 |
| 真正移除 VPN 后的新请求 | 拒绝，服务器零到达 | 同样拒绝，服务器零到达 | 仅该受控场景 |
| 移除 VPN 后的既有 WSS | 已建立连接关闭，未见继续送达 | 分流阶段已阻止建立，缺少存活正控 | 候选仍列未验证，不继承前组结论 |

服务器应用事件包括 HTTP 请求、WebSocket 握手与帧，不等于相同数量的独立请求。修复前后分别使用[基线运行](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/40445028193)与[补丁运行](https://github.com/Ararataki-number-one/yuanying-chat/actions/runs/40448146980)，诊断源为 `e42dc210` 与 `a6635215`。四阶段 Android 用例、服务器及判读控制条件保持相同，补丁另增加二十三项纯 Java 路由政策检查。

补丁只收紧受保护外部 VPN 的新请求准入：需要同接口的双栈默认单播路由，拒绝未知与排除路由，末尾再次检查当前网络。已知不可达路由只视为阻断，不冒充默认单播覆盖。内置固定出口、显式代理与网页生命周期没有改变。

Android 8–12L、仅 IPv4 且阻断 IPv6、以及 /1 分割默认路由布局会被保守拒绝，不等于这些配置已泄漏。每次受保护外部准入最多五次 ConnectivityManager 读取，原为两次；没有增加 DNS 或网站探测，手机性能尚未测量。

两组都有一条带完整 VPN 阶段标签的 Worker 脚本记录。标签不证明到达时的网络状态，当前证据无法确认它属于完整 VPN 活动窗口还是后续切换，既不判为泄漏，也不判为安全。默认路由检查不是系统级断网开关，也不撤销此前已获准的在途请求；同一网络的路由变化及最后一次检查后的变化没有原子绑定保证。

真实手机 Wi-Fi／移动网络切换、完整 DNS、公网 IPv6、Shared Worker／Service Worker，以及内置 Mihomo 全链的真实故障路径，本轮均未执行。整体防泄漏验收尚未完成。强化模式生效确认与指纹一致性属于后续轮次，本补丁没有将它们标为已完成。
