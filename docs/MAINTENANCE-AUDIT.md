### 发布前维护：让验收工具对应当前浏览器

2026-11-13 从开发分支 `1178ce488bc1532d71460845b2b7131724416df6` 继续。此前的生产维护与正式基准完整保留；本轮修复实际失败暴露出的验收工具边界，未增加产品功能。

浏览器导航检查显式区分现有浏览器入口与历史 Dashboard：按实际原生控件、父容器、触摸区域和环境身份验证，支持地址栏横排与窄屏换行。环境详情菜单保留原等待期限，在真实 ScrollView 内有限滚动，最终点击使用已经验证的目标节点坐标。旧 Dashboard 的固定历史输入和原断言仍保留。

折叠工具栏的冷启动检查以实际展开状态为起点，首个点击直接取当前地址控件的真实位置；原八次滑动、返回、HOME/恢复、菜单操作和各段时间预算不变。桌面图片选择宿主只在目标文档已就绪、可见且未导航时安装其等待对象，避免新导航正常清理旧等待对象后，测试仍误认为等待对象必须保留。

两个桌面 Chromium runner 共用一个进程管理模块。输出写入普通文件，避免无人消费的管道阻塞；启动记录保留实际进程和端点等待结果。进程组只有在仍持有原未回收 leader 且 PID、PGID、SID 一致时才能终止，原 TERM/KILL 截止时间覆盖最后等待。浏览器启动参数、页面脚本、控制器与原超时不变。

后台玻璃测量先等待同一进程、同一 Activity 真正 STOPPED，三个可见字段均为 false，所有所属根窗口均为 GONE，且 resumed 目标已离开应用。准备阶段只观察生命周期和窗口，不能用帧数挑选通过样本；其共用 15 秒期限包括命令、存证和解析。随后仍执行原一次 1.1 秒稳定、1.5 秒采样和零新增帧检查。

录屏工具增加有时间戳的日志与真实进程退出观测，仍使用原八秒退出预算；非零退出、超时及最后清理的原判定保留。已有 MP4 或日志中的结束提示都不能替代进程实际退出。工作流补齐嵌套 host 回执和两个 Chromium runner 的原始输出归档，原命令和门禁不因归档改动而变化。

### 文件选择只由一个请求持有

`Attachments` 原来分散保存回调、网址和页面代次，所有选择器共用请求编号 74。取消旧请求会同步调用网页回调，因此回调中新建的选择器可能被旧流程覆盖；旧 Android 选择窗口迟到的结果也无法区分接收者。

现在用私有 `Pending` 集中持有回调、唯一请求编号、原网址和原页面代次。先登记新请求，再撤销旧请求；撤销时先分离回调并结束捕获的旧窗口，再调用网页。结果按原请求编号交付，每次外部回调、URI 授权和窗口操作后重新核对当前 Activity、页面和请求。请求号在本进程内不循环复用，耗尽时明确返回失败；不声称恢复 Android 进程死亡前的请求。普通 MIME、多选、持久 URI 授权与 DownloadsProvider 的行为保持原样。

### Gecko 的首个 SDK 窗口与网页准入分开

固定 Gecko 157 源码中，已安装扩展在 `APP_STARTUP` 时等待首个窗口发出的启动事件；原应用又在等待该扩展的 native 路由桥接后才创建第一个窗口。新安装和已安装冷启动因此可能表现不同。

新增的临时启动窗口只完成 SDK 初始化：无 surface、无页面桥接、无 `loadUri`，导航和新窗口请求全部拒绝，不充当 `primary`、`current` 或 `ready`。实际网页仍需原有 identity、checkpoint、route、headers、privacy 和 native protection 条件全部成立。正常打开、失败、扩展停用和 destroy 统一释放临时实例；即使 SDK 在退出回调之后才完成打开，也按捕获的旧实例补充关闭，不关闭后来替换的新窗口。原启动闭锁代理和网络保护没有移除。

### 历史证明读历史，当前行为执行当前代码

新增的 `tests/historical_source_inputs.py` 只读取固定正式提交 `7383bb1…` 的真实 Git 对象，逐级核验 commit、tree、path、mode 和 blob 身份，拒绝缺对象、符号链接及越界路径；没有当前源码回退，也不会自动联网。所需对象由显式构建准备步骤取得。

历史消费者明确选择这个入口，原逆差异算法、fixture、旧断言和负控保留。真正执行当前 Java 方法、当前 UI runner、工作流步骤、发布脚本、页面归属及故障变体的检查仍读工作树。工作流中新加依赖准备作为独立步骤，不能改写原步骤来绕过顺序与内容比较。此调整减少继续叠加整文件反向适配的必要，不代表删除了所有既有历史适配代码。

### 验收工具复用已有记录协议

玻璃验收复用 `integration_event_contract.ReceiptJournalDiscovery`，从原生持久事件日志发现已经提交的事件，避免单独依赖可能丢失的 logcat 提示。来源、APK、nonce、动作、命令、序号与摘要检查保留；读取也受原截止时间约束。设备横屏先设置竖屏基准再锁定实际旋转，继续要求真实视口精确匹配，并核对恢复结果。未修改正式 AGSL、CPU 材质或空闲帧预算。

后续实际设备日志又暴露了模拟器准备边界：Android 15 桌面的 `NOSENSOR` 恢复会撤销在桌面设置的旋转，API 32 的默认 AVD 没有创建屏幕导航栏。准备流程现在先进入原有原生配置页面，再锁定方向并读取稳定的实际配置；AVD 明确使用屏幕导航键，保留硬件与系统属性回执。观测仍核验真实尺寸、字体、系统栏与每个字体 nonce 的完整唯一结果，不把命令成功当作实际状态成功，也不丢弃旋转重建留下的重复观测来通过检查。

设备准备另观察实际默认 HOME、当前 resumed Activity 与输入焦点，防止只看到 `sys.boot_completed=1` 就在系统初始化页面上启动应用。独立 45 秒共用截止时间涵盖命令、解析与保存；当前 ANR／错误窗口直接拒绝，保留完整系统日志。应用配置页面完成方向稳定后也必须释放：相同组件的后续启动可能只进入旧实例的 `onNewIntent`，并不执行新字体 nonce 或聊天场景的 `onCreate`。这两步是测量之前的环境准备，均不代替业务就绪与设备结果。

干净 CI 的历史准备同时纳入原有两个 UI owner。原 21 组历史清单、既有 UI manifest 和各自文件 pin 保持原样；缺失对象只能在实际仓库与事件身份成立后取回。统一回归记录这两个准备依赖的指纹，避免本地已有 Git 缓存掩盖构建不完整。

### 纹理内容更新与显示表面生命周期

实际派生 SDK 的 `SurfaceViewWrapper` 在每次纹理内容更新时重新构造 `Surface` 并通知恢复／调整 compositor；同尺寸的连续内容帧也会重复走这条路径。设备的原空闲失败窗口记录到持续 TextureView buffer，而原生玻璃动画和文字变化计数没有对应增加。固定 SDK 类字节的因果宿主进一步复现：12 个同尺寸内容更新产生 12 次额外表面提交和分配。

新增 `GeckoTextureSurface` 只负责这个边界：记住当前纹理和尺寸，把真实 available、size、destroy 事件交还原监听器，消除同一纹理同尺寸的重复 update 重设。它通过公开 `TextureView.SurfaceTextureListener` 绑定，没有反射、定时器、Activity 或全局状态。重复安装可复用当前绑定；SDK 更换 listener 后，旧绑定不能夺回它；关闭时只归还自己仍持有的 listener。

Gecko 明确请求替换失效表面时，公开的 `requestNewSurface()` 接点记录一次待恢复请求，并继续调用原 SDK 的异步可见性切换。下一次有效更新会新建并提交表面，即使纹理和尺寸相同；普通尺寸变化不提前消耗该请求，因为原 SDK 此时仍提交旧 `Surface`。标记在转发前清除，保留同步回调中发生的下一次请求，并由销毁与关闭清理归属。

`GeckoWebView` 仅保留一个绑定字段，在既有后端准备好后安装、实际 session 释放后关闭。网页正常帧交付不由此组件暂停或节流；AGSL、CPU 降级、原视口与空闲预算没有调整。完整 SDK 字节模式、原协作源码模式及实际 Android API 编译各自记录范围，最终效果仍由同源设备门禁决定。

这轮仍按已复现缺陷收拢职责，没有为缩短文件而一次性拆散所有大类。后续可维护性来自明确的对象归属、统一清理路径和实际行为回归，不能用新增小类数量或文件行数作为完成标准。

### 文件保存宿主的退休等待与原始错误

文件保存宿主先检查 `worker.isShutdown()`，再提交空任务等待队列排空；两步之间真实 `close()` 可以关闭 worker，使这次提交被拒绝。现在直接提交等待任务，仅在实际已关闭的 executor 拒绝提交时等待其终止，随后继续原有 UI 队列屏障。运行中的拒绝、失败 Future 和原五秒超时仍失败；没有重试或增加等待预算。生产文件保存逻辑未因此修改。

宿主的 JVM 退出码、stdout、stderr 同时保存在原文本文件与独立 `.run.log`；即使没有生成有效 JSON，异常也包含真实退出信息。非零 JVM 退出不能留下通过状态，工作流另外归档原始文本文件。此改进解决错误被二次 JSON 异常遮蔽的问题，不把缺失的旧日志补写成已知原因。

## 主要发现与处理顺序

### 1. 页面导航与任务忙碌状态耦合

`ChatSession` 同时维护网页、回复、文件操作、网络准备和页面恢复。把“有任务”直接用于拒绝地址切换，会把任务调度策略变成浏览器导航限制，产生用户截图中的问题。仅更换提示文字或逐个删除 UI 判断不能建立稳定的行为边界。

本轮规则是：用户可以离开当前网页；原页面专属的选择器、脚本请求和迟到回调按原页面归属处理，独立下载或原生任务不能因为换网址而被整体取消。环境身份、公共网址校验、网络与指纹准备仍各自保持原有约束。URL 输入被接受与网络请求具备发出条件，是两个独立状态。

本轮由 `ChatSession` 的导航边界和实际调用方统一处理，使用明确的调用结果。后续不能再从某段状态文字推断导航是否成功，也不能复制一套 `busy` 判断到每个按钮。

已接受的用户目标通过已有 `browsingUrl` 与一个明确的选择标记保留。连接完成、连接失效后重试或暂时离线时，旧原生页面／旧任务的地址不能覆盖较新的用户输入；没有显式用户选择时保留原有恢复优先级。地址显示同样读取这个目标，避免离线接受新网址后又显示旧页面地址。仍在截图或导航中的页面，也不能被网络回调误判为已经保留的旧页面。

`beginNavigation` 返回的页面代次同时用于 Gecko 的时区重开、进程恢复、关闭弹窗返回和资源延迟启动。调用方通过一个无状态的检查核对原生页面及代次，防止同步回调已打开新地址后，外层旧恢复再次覆盖。关闭弹窗时，即使返回父页的导航已过期，旧弹窗的端口、路由租约和原生会话仍必须清理；页面提交回调发生重入后也不能继续发出旧页面的完成回调。

### 2. Chromium 导航前清理重复，且存在同步回调重入问题

审查起点的 `BrowserActivity.go`、`history`、`reloadOrStop`、初始页面启动及 `onPageStarted` 都分别操作文件选择、权限、指纹绑定和页面代次。`BrowserFiles` 和 `BrowserPermissions` 的取消过程会调用网页回调；它们自身已处理部分重入，但调用方随后仍使用可变的 `selected` / `web()` 继续旧操作。

因此，取消旧选择器时如果回调已经打开新地址、切换标签或关闭页面，外层旧操作仍可能覆盖新地址，或作用于另一标签。另一个较小问题是：没有可返回历史时，调用 `history` 也会先取消当前文件选择器。

本轮处理：

- 集中到 `beginPageNavigation`，使用既有 `Tab.generation`，不另设竞争的页面状态机。
- 在取消回调之前使旧页面绑定失效；每次回调之后重新核对标签、WebView、选择状态和页面代次。
- 地址输入、历史、重载、初始启动和原生页面开始回调复用该边界。
- 地址等待网络或指纹准备时保留最新输入；原有准备约束仍决定何时真正加载。
- 无历史可走时直接返回，不撤销当前页面的选择器。
- 停止加载使旧导航代次失效，防止取消回调之后外层旧加载继续执行。
- 只取消页面选择器与权限请求，不调用独立下载取消入口。

修复由编译当前生产方法的行为测试覆盖，包括同步回调内再次导航、切换标签、销毁、停止、等待网络、原生开始回调和独立传输边界。测试不以“出现了某个新方法名”代替行为验证。

### 3. 大类与单行状态操作降低可读性

`GeckoWebView` 包含内核回调、桥接、文件、生命周期和渲染相关职责；`ChatSession` 涉及网页与原生任务两种生命周期；`BrowserActivity` 同时拥有界面、标签页、指纹准备、持久化、自测和导航。当前已有不少合理的独立策略类，继续无边界增加小类也会让调用链更难追踪。

本轮仅把重复的导航清理变成一个有明确前后条件的操作，并展开被修改的导航方法。没有对整仓库批量改格式，也没有声称已经拆完这些大类。

后续结构调整建议按以下顺序，每次只迁移一项责任并保留原行为：

1. 明确页面生命周期与独立原生任务生命周期的归属，回调统一携带已有的页面／环境身份。
2. 将 Chromium 指纹准备与持久化协调从 Activity 中分离，Activity 只保留生命周期转发和界面更新；不能把原有网络保护移出检查链。
3. 梳理 `MainActivity` 的重载、草稿保存和页面恢复流程，确认原语义后再提取；本轮没有完成这项迁移。
4. 对 `GeckoWebView` 按内核事件、网页桥接和文件请求分阶段整理；不要为减少文件行数而把共享状态原样散落到多个工具类。

### 4. 历史源码适配层本身已形成维护负担

大量历史测试通过源码片段、全文哈希和反向差异恢复旧视图。这类检查可保留旧发布证据，却不能代替“当前生产代码是否满足行为”的回归。普通重构如果必须不断补一层历史投影，会使测试维护成本和生产代码维护成本一起增长。

本轮继续使用已有的 Chromium 行为执行器，编译当前方法，保留原断言和原有故障注入，并加入同步重入的回归与故障注入。不新增历史源码投影适配器。

后续应把两种职责明确分开：

- 发布归档证据：固定到原提交运行，记录其原始源码与结果。
- 当前行为检查：编译当前代码，验证页面所有权、资源生命周期、环境隔离和网络保护。

迁移任何旧检查前，必须先列出它保护的行为和对应的新检查；不能通过删除断言、放宽失败条件或修改历史证据来换取绿灯。当前全量历史回归存在的问题仍需单独处理，不因局部行为测试通过而视为全部通过。

### 5. 空异常处理需要分类审查

起点源码中精确匹配 `catch(Exception ignored){}` 的位置有 108 处，`catch(RuntimeException ignored){}` 有 34 处。这不是 142 个已确认缺陷，也不是所有异常处理的完整统计：不少是销毁已关闭对象、取消已失效回调或读取可丢弃缓存时的合理容错。

## 第二轮：后台事务与启动批次的责任边界

### Chromium 指纹事务独立成完整组件

原 `BrowserActivity` 为加载、核对、激活、保存、撤销和记录自测结果分别组织后台任务和主线程回调。相同的队列、异常与生命周期处理重复出现，单独审查持久化行为必须同时理解 Activity 的页面状态。

新增 `ChromiumFingerprintJobs` 统一管理串行 I/O、提交时的数据快照、结果交付和关闭。它使用应用级环境 Context，不持有 Activity、Tab 或 WebView，也不新增页面代次。责任如下：

| 责任 | 所在位置 |
| --- | --- |
| 页面、标签、原生能力确认、网络许可和当前 binding | `BrowserActivity` |
| 加载、保存 / 轮换、策略核对、activate / record / retire 的串行编排 | `ChromiumFingerprintJobs` |
| 环境身份、文件锁、revision 比较与持久化内容 | 原 `ChromiumFingerprintStore`，语义保持不变 |

Activity 通过包内 `createFingerprintJobs()` 工厂创建一次协调器。真实 Worker 集成测试从这里注入自己持有的串行队列，使测试 fence 与实际保存 CAS 使用同一队列；生产 Jobs 的 worker 保持私有，测试不再直接依赖 Activity 裸线程字段。

任务提交时先复制 JSON，后续调用方修改对象不会改变已经排队的写入。关闭组件后，已接受的写入按原 `shutdown()` 语义继续排空；旧 Activity 的迟到结果停止交付。工作队列拒绝执行会回到明确的失败分支，不能使 loading / saving / pending 状态永远等待。

这次不是单纯搬动代码。完整的新组件由真实 Store / Spec 的宿主执行器验证；Activity 的现有导航检查继续保留，并补充原来没有实际执行的加载、保存、核对和激活路径。

### 自测失败的停网决定独立于记录写入

原 `finishFingerprintObservation` 只有在 `Store.record` 成功后才暂停保护模式下自测失败的网页。对真实 Store 注入写入失败后，原生产方法成功编译，却在“失败自测仍应暂停联网”断言处失败；因此这是已复现缺陷，不是对空 catch 的猜测。

修复将当前页面的流量许可撤销放在持久化之前。存储失败影响记录与提示，不再决定该页面是否能够继续联网。兼容模式的既有行为保留。

页面归属与允许联网分开检查：当前失败页面即使已经暂停，也能接收自己的结果保存回调；旧页面、旧 provider、旧 binding、较早导航或已销毁 Activity 仍不能接收该回调。停止、取消选择器等动作可能同步重入，之后重新核对原页面，避免旧清理继续作用于新导航。

### 合并网络重启由一个启动批次持有变更租约

原 `NativeNetwork.runStartOperation` 在发现 `restartQueued` 后，另排一个裸 worker 继续重启并返回。外层 `finally` 随即释放 `ChromiumRouteLease` 的变更句柄，导致第二轮启动仍在运行时，新网页和下载却能进入。使用实际两个生产方法和完整 `ChromiumRouteLease` 的第二轮启动栅栏已复现此问题。

现在由外层 worker 在同一个 `try / finally` 内循环处理已合并的重启，最终统一释放句柄。没有增加新的持久状态或重复的队列标记，网络操作仍在同步锁之外。等待者继续在最后一轮获得同一不可变终局结果，`RECOVERED`、`RETAINED` 和 `FAILED` 的原有区别保留。

已合并的启动连续执行，其他 worker 队列任务不再插入两次启动之间；这是此次明确的调度变化，符合原先所有等待者都等最终一轮的批次语义。队列拒绝执行时，同一批次的等待者、排队标记和变更句柄也完整收尾；释放监听器重入时不会清掉较新的批次。

原 43 项启动观察断言按原名称和顺序保留，另补真实租约、连续重启、失败、拒绝执行和释放监听器重入场景。启动签名变化的当前宿主与集成 fixture 同步迁移，不增加历史源码投影。

## 第三轮：任务终局保存与 Gecko 页面归属

### 任务结果的保存有明确成功条件

原 `ChatSession.completeReply` 和 `WebReplyObserver.finishStopped` 通过普通 `delivery` 更新任务记录。该方法吞掉数据库异常、没有返回成功与否；调用方随后仍清除 `pending` 并宣布完成或停止。缺失记录、零行更新、SQLite 写入异常，以及偏好设置提交失败都需要区分。原源码在故障注入宿主中成功编译并复现了这些问题。

新增无持久状态的 `ReplyTaskPersistence`，统一完成、观察到停止、解除等待与终局恢复的顺序。这个类只协调既有记录，不新增数据表、状态字段或恢复协议：

| 结果 | 处理规则 |
| --- | --- |
| SQLite 记录不存在、更新零行或写入异常 | 保留当前等待对象，不发完成通知、不停止其服务，报告保存失败。 |
| SQLite 已记录 `completed` / `stopped`，偏好设置清理成功 | 结束当前本地观察，按既有规则通知及结束服务。 |
| SQLite 已记录终局，偏好设置清理失败 | 终局仍以 SQLite 为准；报告清理未完成，重启后清理遗留 pending，不重新恢复已结束的观察。 |
| 用户解除等待，记录状态为 `uncertain` | 它不代表网页已完成或停止；必须成功清理 pending 才宣告解除，失败时可重试。 |

`DeliveryStore.update` 现在返回明确结果：已存在的相同记录算成功，真正写入必须影响一行；失败不能推进 revision。普通进度缓存也仅在更新成功后保存去重签名，终局路径直接核对数据库，不依赖这个缓存。

Android 偏好设置的 `commit()` 可能已经改变内存、触发监听器，最后仍报告写盘失败。因此提交之后重新核对 pending 对象与环境是否已删除；完成通知和停止服务之后继续核对现有工作代次，防止旧任务的收尾停止或覆盖回调中新建的任务。冷恢复沿用原通知去重账本，不增加新的通知机制。

这仍不是 SQLite、偏好设置和 Android 通知之间的原子事务，也不宣称在任意断电与系统服务故障下通知恰好发生一次。故障回归使用明确的文件保存模型与服务边界，实际 Android SQLite/WAL 和通知生命周期须由设备验收另行证明。

### 页面激活和关闭属于同一个生命周期事务

原 `GeckoWebView.activate` 先释放 native surface，再取消旧桥接请求；取消会同步执行消费者。消费者可能已经接受新网址、选择另一弹窗或销毁环境，外层旧激活仍继续把 current 改成原目标。这一顺序问题已用完整生产方法与实际 `BrowserBridgeRequests` 复现。

修复先保留可用的旧 surface，取消旧请求后重新核对现有导航代次、current 和目标跟踪身份；配置与阅读回调之后也检查归属。新增 popup 在 Gecko 打开前可以处于 closed 状态，这一合法流程继续保留，不能用一个笼统的 `isOpen()` 条件拒绝所有新窗口。

交叉审查进一步发现，单改 `activate` 无法修好它的调用方：`closePopup` 已提前移除旧弹窗，即使激活因新导航而退出，尾部仍会关闭承接了新导航的 old session。完整 `closeWebsitePages → closePopup → activate` 组合红测确认了这一问题。

现在旧弹窗在 current 真正交给其他 session 之前继续被跟踪。如果较新的命令仍拥有这个 surface，旧关闭操作停止；已经让出 current 的旧弹窗则完整释放。最终退休先撤销跟踪身份，再通知线路租约监听器和剩余桥接消费者，防止回调重新选中正在关闭的对象；取消消费者抛异常时仍通过 finally 关闭已退休的 native session。原独立下载租约、返回父页和关闭全部网站行为继续保留。

### 保留浏览器会话，释放旧 Activity

`ChatSession` 长期持有 Gecko 视图，但旧 `MainActivity.onDestroy()` 只解除显示 context，没有移除安装在视图上的页面客户端、附件客户端、下载监听和响应下载回调。它们分别引用 Activity、Attachments 或 FileDownloads，形成四条保留旧界面的强引用链。迟到的外部响应也仍可能进入已经销毁的 FileDownloads。

新增 `GeckoUiBinding` 专门持有一次 UI 安装的回调身份和父容器。销毁时只解绑本次仍拥有的对象，将页面客户端恢复为会话自身的客户端，保留后台页面、错误处理和阅读缩放行为。父容器、display context 及辅助页也按 host 身份释放，旧界面迟到销毁不能移走新界面的浏览器。

移除 View、关闭辅助页、取消审计等操作可能同步调用其他代码。因此 `releaseHost(expectedActivity)` 先让出旧 context，再触发退出回调；`onPause()` 在共享会话操作之间复核 host 身份。自身 handler、observer、界面反馈始终清理；回调中已绑定的新 host 不再被外层旧 pause 改为后台。原无参数 `remoteClient()` 覆写入口完整保留，现有 APK fixture 无需迁移。

验证包含真实安装对象的强引用遍历、迟到下载分派、后台 session client 回调及同步重入。这证明声明的宿主模型中旧引用已解除，不等于真机 heap 测量或内存占用下降的量化结论。

### 取消下载与重新下载共用私有副本清理

原取消路径直接排队 `file.delete()`，没有文件租约或持久任务归属检查。旧界面释放任务后，新界面可以领取同一记录并写入，而旧 worker 随后仍可能删除该文件。原路径还先将 `complete` 清零，可能在取消记录未持久化时丢失完整副本的恢复依据。

现在两条清理路径共用 `retirePrivateCopy()`：先确认既有 `taskGeneration` 并持久化 `partial → retiredPartial`，成功后才清除内存中的旧副本状态。真正删除前获取既有 `SealedFileIo` 租约，等待结束后再次核对权威记录、任务代次和归属；最后的回调也不能释放新领取的任务。

`beginPartialRetirement()` 仍限于重新下载时的未完成副本；明确的 `beginCancelledCopyRetirement()` 才允许用户取消完整的私有副本。待确认目标 `pendingDestination`、已保存 URI、未知完整性、其他记录引用和非法路径继续受保护。合法缓存已被系统移除时，可以确认取消，不会留下永远无法取消的任务。文件租约、行格式和环境隔离协议均复用已有实现。

### 另存为必须确认流关闭

原另存逻辑在 try-with-resources 关闭前就设置复制成功；文件提供方在 `close()` 报错时，失败清理会被跳过。循环内部的生命周期检查也覆盖不到空文件或最后一次 close 期间退出。

现在复用 `SavedFileBytes.copy()`，在打开输出前和输入、输出全部关闭后核对生命周期。只有所有阶段成功才结束复制。目标 URI 仍在租约内核对是否被已有下载索引引用；原文件与已索引文件不会进入清理路径。提供方拒绝删除或抛错时明确报告“目标副本清理未确认”，不把未确认写成清理成功，也不宣称目标一定仍存在。旧 picker 结果、已关闭 executor 和已退出 Activity 的反馈同样有明确终点。

### 同网址刷新仍是新的权限文档

`BrowserPermissions.prepare()` 会先拒绝上一条请求，这个回调可能同步重新加载同一网址。原逻辑只比较 URL，然后读取新的 generation，导致旧请求被绑定到新文档。现在在回调前捕获已有文档代次，回调后同时核对代次、当前 WebView 和 Activity 状态；没有新增权限状态字段或改变授权范围。

### 保留失败判定，补足设备启动诊断

已补齐 `2ef73a2` 的设备终态：API 35 玻璃场景 4 / 7 通过，长按 7 / 7 都进入环境选择；失败为阅读绘制 5 / 9 帧超过 2 帧预算，以及后台 1 帧超过 0 帧预算。独立追加诊断三次均未观测到绘制或玻璃/文字属性变化，因此不能据此断言是玻璃动画循环。

API 32 横屏请求与实际 viewport 不符，工具按要求拒绝验收并确认恢复默认 display；后续七个场景均在 ready 前超时，fixture 请求数为零。原日志未采集既有 `PocketCollapseTrace`，不足以定位启动原因。本轮仅在 ready 已失败后保存有界启动输出、当前 nonce/源码身份对应的原生计数器，以及不含 URL 的 resumed Activity 记录；诊断出错也不覆盖原失败。等待期限、长按路径、空闲帧预算及配置门槛均未放宽。工具改进不代表上述设备问题已经修复。
