# 2.0.7：减少真实网页新连接的握手等待

本次目标是缩短打开网页、建立新请求连接的等待，不再把减少测速次数称为显著提速。

## 改动

已有 Mihomo 固定出口预认证原先只保留一条备用连接。网页一次建立多个连接时，只有第一个请求能使用它，其余连接仍需完整经过入口建连、出口协商和认证。

现在固定出口配置最多四个预认证槽位。只有真实连接成功后才按需补充，备用连接只完成代理认证，不发送 ChatGPT 请求，不预先 CONNECT 到目标网站。新请求原子领取可用槽位；没有备用连接就正常建连，不等待预热，也不排队限流。

保留原有保护：八秒到期、线路与配置代次绑定、网络变化失效、资源压力停用、停止时取消；HTTP 请求和上传内容不会被自动重放。单次 URL 测速继续绕过预认证池，显示值不会因此被人为降低。手工出口与出口订阅使用相同设置，入口和固定出口均不自动更换。

代价是每个正在建连的环境最多多准备四条短时代理连接，可能增加少量流量和资源占用。没有定时补池；没有真实请求时不会循环创建备用连接。已建立的 HTTP/2、WebSocket 长连接仍优先复用。

## 实测范围

第一轮本地真实 socket 对照，在冷建连、方法协商、认证及 CONNECT 阶段各注入 60 ms 延迟，等待预认证完成后发起四个并发连接：

- 原来一条备用连接：全部就绪约 245.5 ms。
- 四条备用连接：全部就绪约 61.3 ms。

这证明在准备就绪、网页同时新建连接的场景下，握手等待可被移出请求关键路径。该测试不是公网、用户手机、页面可用时间或 ChatGPT 生成速度测试，不能写成“网速提升四倍”或“400 ms 已降到 200 ms”。

新增 Android 回归使用真实 Gecko HTTP/2 请求、真实受控 SOCKS5 入口和固定出口，分别核对一槽与四槽的请求、认证、CONNECT 时间与服务端连接编号。既有单槽隔离、切网、拒绝认证、取消和 WSS 保持回归继续保留。

## 手机验收

同一手机、同一 Wi-Fi、同一入口、同一固定出口、同一网站分别对比旧版与候选版：首次进入会话、热打开、附件选择后开始上传、文件下载开始时间；分别记录三次以上。不要将入口单测、出口单测、完整链路和网站首响应混在一起比较。

如果连接复用后的完整线路仍为 400 ms，扩大预认证池不会把这个往返时间变成 200 ms。后续需要通过真实同口径数据判断入口到固定出口的路由、丢包或拥塞；固定出口路径本身没有更快线路时，客户端不能承诺减半。此时应明确呈现限制，不更换测速口径制造“提速”。
